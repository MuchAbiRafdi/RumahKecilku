# Audit keamanan Rumah Kecilku

**Tanggal:** 22 Oktober 2026  
**Cakupan:** tinjauan kode frontend/backend, autentikasi dan sesi, seluruh router API yang terdaftar, validasi input, repository SQLite, batas role dan relasi anak, konfigurasi Next.js/preview, serta tes regresi.  
**Jenis audit:** pemeriksaan source code dan tes otomatis pada workspace ini; **bukan** penetration test, audit infrastruktur/cloud, verifikasi legal, atau sertifikasi klinis.

## Kesimpulan

Rumah Kecilku tetap **prototipe demonstrasi**, bukan sistem yang disetujui untuk menyimpan data identitas, foto, atau kesehatan anak nyata. Fondasi tenant/organisasi, cakupan anak di API, role admin operasional, kredensial sensor per perangkat, dan alur demo check-in/out dengan penjemput berizin telah ditambahkan serta diuji silang-tenant. Namun onboarding lembaga, undangan staf dan verifikasi identitas independen, kontak darurat, modul keselamatan penuh, enkripsi data, tata kelola audit/retensi/persetujuan, dan kontrol operasi produksi masih belum tersedia.

Untuk mencegah salah konfigurasi yang berbahaya, `RUMAH_APP_ENV=production` sekarang **menolak startup** dan menjelaskan blocker. Penguatan kode maupun tes tidak dapat menjamin aplikasi “tidak akan diretas”; sistem produksi tetap memerlukan desain, infrastruktur, pengujian independen, dan operasi keamanan.

## Temuan dan status

| ID | Risiko | Temuan | Status |
|---|---|---|---|
| RK-01 | Tinggi | Endpoint pendaftaran dahulu menerima role caregiver/dokter dari payload, sehingga pengguna dapat meminta hak staf tanpa verifikasi. | **Diperbaiki:** pendaftaran mandiri hanya menerima/default ke `parent`; tes memastikan role staf ditolak. Akun staf tetap harus dibuat melalui undangan/verifikasi institusi yang belum ada. |
| RK-02 | Tinggi | Akun demo bersama di-seed/diperbaiki saat startup dan memakai kredensial yang diketahui. | **Dibatasi:** seed hanya berjalan dengan `RUMAH_DEMO_MODE=1` pada `RUMAH_APP_ENV=preview`; login identitas demo ditolak di luar mode demo, termasuk akun demo lama. Kredensial bersama masih tersedia di preview sintetis dan tidak boleh dipakai pada data nyata. |
| RK-03 | Kritis untuk penggunaan multi-lembaga | Sebelumnya data pengasuh/dokter bersifat global. Sekarang terdapat `daycare_organizations`, membership aktif, profil anak dengan pemilik organisasi, dan cakupan server-side pada roster, aktivitas/foto, kehadiran, observasi/laporan/KPSP, pesan/notifikasi, menu, dan sensor. | **Diperkuat sebagian:** ada tes dua tenant dan akses ditolak. Belum ada onboarding/invitation admin/platform, data migration wizard untuk instalasi lama, verifikasi relasi wali yang independen, room/shift domain, dan audit independen. Jangan menganggap siap untuk data nyata atau deployment multi-daycare operasional. |
| RK-04 | Tinggi | Belum ada verifikasi email/identitas staf, undangan staf, atau MFA. Relasi keluarga hanya memakai alur demo terbatas: admin mencatat konfirmasi pemeriksaan institusi lalu akun parent menyetujui; tidak ada pembuktian identitas independen atau penyimpanan bukti pemeriksaan. | **Belum diperbaiki — blocker produksi.** Pendaftaran parent-only mencegah eskalasi role, tetapi alur terbatas ini tidak membuktikan seseorang adalah orang tua dari anak tertentu secara independen. |
| RK-05 | Tinggi | SQLite berisi catatan, ringkasan, dan foto data URL tanpa enkripsi aplikasi at-rest. | **Sebagian diperkuat:** file database POSIX dibuat/dibatasi ke mode `0600` dan proses memakai umask privat; request dibatasi 5 MiB. **Ini bukan enkripsi.** Foto dan isi database tetap terbaca bagi proses/akun host yang memiliki akses. |
| RK-06 | Tinggi | Siklus persetujuan, pencabutan persetujuan foto, retensi/penghapusan terverifikasi, audit tahan perubahan, backup terenkripsi, serta prosedur insiden belum lengkap. | **Belum diperbaiki — blocker produksi.** Foto masih disimpan dalam SQLite; jangan mengunggah foto atau identitas anak nyata. |
| RK-07 | Menengah–tinggi | Sesi sebelumnya dapat memakai token bearer/browser dan tidak memiliki MFA atau kontrol sesi multi-perangkat yang matang. | **Diperkuat:** token mentah hanya dikembalikan/diterima pada preview sintetis dengan dua flag eksplisit; selain itu hanya cookie sesi. Token database tetap di-hash, cookie HttpOnly/SameSite=Lax, masa berlaku 12 jam. MFA, revokasi semua sesi, dan rotasi pasca-perubahan kata sandi masih belum tersedia. |
| RK-08 | Menengah | Percobaan login sebelumnya tidak dibatasi dan dapat membedakan akun berdasarkan respons. | **Diperkuat:** pesan kegagalan generik, verifikasi hash dummy untuk identitas yang tidak cocok, dan batas 10 kegagalan per alamat akun per 15 menit dengan respons 429. **Belum ada** rate limit global/per-IP di reverse proxy; banyak alamat berbeda masih dapat membebani layanan. |
| RK-09 | Menengah | Respons API sensitif dapat tersimpan di cache; belum ada pembatasan ukuran request dan host eksplisit. | **Diperkuat:** header no-store, anti-sniff/frame, CSP API, Referrer/Permissions Policy, Trusted Host allowlist, batas body 5 MiB, dan header browser pada Next.js. CSP Next masih mengizinkan inline script/style yang diperlukan framework; ini bukan perlindungan XSS sempurna. `'unsafe-eval'` hanya dipakai ketika Next berjalan dalam mode development (termasuk preview dev untuk rekonstruksi call stack React) dan tidak dipakai pada `NODE_ENV=production`. |
| RK-10 | Tinggi untuk telemetri | Sensor sebelumnya memakai satu `RUMAH_SENSOR_API_KEY` global. | **Diperbaiki pada kode:** perangkat didaftarkan ke satu organisasi/ruang, menerima secret acak unik yang hanya dikembalikan sekali, secret disimpan sebagai hash, dan pembacaan dicatat/dibaca menurut organisasi. Tidak ada UI manajemen/pencabutan perangkat lengkap; produksi tetap memerlukan secret store perangkat, rotasi/revokasi, TLS, dan audit independen. |
| RK-11 | Menengah | Dependency perlu dipantau dan backend belum memakai lock file/hash yang membuat instalasi dapat direproduksi secara ketat. | **Pemindaian 22 Okt 2026:** `npm audit` menemukan 0 advisori; `pip-audit -r backend/requirements-dev.txt` tidak menemukan kerentanan yang diketahui. Ini hanya snapshot dependency yang dapat di-resolve hari itu, bukan audit seluruh rantai pasok; backend masih memakai rentang versi tanpa lock/hash. |
| RK-12 | Tinggi | Admin operasional baru sebelumnya tidak ada; akses admin berisiko tercampur dengan data klinis jika hanya diberi role staf umum. | **Diperkuat:** role `admin` dibatasi ke roster/kehadiran/katalog/sensor, sementara endpoint aktivitas, observasi, dan KPSP menolak admin. Ditutup oleh tes backend; tetap perlu review permission lengkap dan admin UI tidak menampilkan detail klinis. |
| RK-13 | Tinggi | Serah-terima pulang sebelumnya hanya berupa status hadir/izin/sakit, tanpa daftar penjemput atau riwayat check-in/out. | **Diperkuat sebagian:** admin kini mencatat nama/relasi penjemput setelah merekam metode konfirmasi parent di luar aplikasi; caregiver memilih kontak aktif, mengonfirmasi pencocokan langsung, dan mencatat check-in/out. Jejak waktu/actor disimpan; tidak ada nomor/foto identitas. Pencocokan nama bukan verifikasi identitas independen, dan audit belum append-only/tahan perubahan — blocker sebelum data nyata. |

## Penguatan yang diterapkan

- `backend/app/models/schemas.py` dan `backend/app/api/routes/auth.py`: role registrasi dipatok `parent`; token browser tidak dikirim kecuali dalam preview sintetis.
- `backend/app/repositories/auth_repository.py`: seeding demo bersifat opt-in; counter pembatasan login menyimpan hash pengenal, bukan email mentah; migrasi role menambahkan admin tanpa mereset akun; schema organisasi, membership, profil anak, dan cakupan akses; daftar admin/caregiver/doctor berasal dari tenant aktif.
- `backend/app/repositories/activity_repository.py`, `attendance_repository.py`, `observation_repository.py`, `development_report_repository.py`, `message_repository.py`, `notification_repository.py`, `meal_repository.py`, dan route KPSP: query/mutasi child-scoped memakai daftar anak yang diberikan server dari membership/tautan akun, bukan daftar ID dari browser.
- `backend/app/api/routes/children.py`: roster tenant, pembuatan profil, edit nama/tanggal lahir/ruang, serta pembacaan audit profil hanya admin tenant; audit profil menyimpan actor dan nama kolom yang berubah, bukan nilai sensitif sebelum/sesudah. `backend/app/api/routes/attendance.py` membatasi check-in/out ke caregiver/admin, daftar penjemput aktif ke caregiver/admin, pembuatan/pencabutan izin dan audit ke admin, serta catatan kehadiran ke cakupan anak sesi; dokter tidak menerima nama penjemput.
- `backend/app/repositories/attendance_repository.py`: catatan check-in/out dan perubahan izin penjemput memuat waktu lokal, actor, nama/relasi minimum dan status; penjemput dicabut secara soft revoke dan tidak dapat dipakai untuk check-out baru. Ini kontrol operasional demo, bukan verifikasi identitas atau audit tahan perubahan.
- `backend/app/repositories/sensor_repository.py` dan `backend/app/api/routes/sensors.py`: secret unik per perangkat/organisasi, disimpan sebagai hash; telemetry lama tanpa kepemilikan organisasi sengaja tidak ditampilkan.
- `backend/app/api/dependencies.py`: bearer/custom session headers diterima hanya dalam preview sintetis yang secara eksplisit mengaktifkan token browser; di mode lain hanya cookie.
- `backend/app/core/runtime.py`: konfigurasi ketat dan penolakan startup produksi sampai blocker utama diatasi.
- `backend/app/core/middleware.py` dan `backend/app/main.py`: ukuran request dibatasi, host divalidasi, respons API tidak di-cache, header keamanan dipasang, dokumentasi API tidak dibuka pada konfigurasi produksi, dan permission database lokal diperketat.
- `backend/app/repositories/auth_repository.py` dan `backend/app/api/routes/children.py`: tautan wali dibatasi tenant, memerlukan pemeriksaan institusi oleh admin dan konfirmasi akun parent, tercatat di audit, dapat dicabut, serta hanya tautan berstatus `verified` yang membuka cakupan anak. Tautan legacy yang tidak punya metadata verifikasi dimigrasikan ke `pending`; seed keluarga demo tetap berlabel sintetis.
- `frontend/components/AccessPage.tsx`: kontrol pendaftaran role staf dihapus; daftar akun demo hanya tampil ketika `NEXT_PUBLIC_DEMO_MODE=1`.
- `frontend/next.config.ts` dan launcher preview: CSP/header browser ditambahkan; flag demo dan token didefinisikan hanya oleh skrip preview yang eksplisit.
- `backend/app/ai/development_insights.py` memberi ringkasan bukti terstruktur dan langkah terpisah untuk pengasuh/dokter; jawaban KPSP mentah dan isi catatan bebas tidak dikirim ke pihak ketiga atau ditampilkan di kartu insight. `backend/app/ai/mock_activity_model.py` melatih Multinomial Naive Bayes lokal dari 96 skenario mock yang sepenuhnya sintetis di `backend/app/data/mock_activity_training.json`; classifier hanya memilih kategori ide aktivitas umum. Tidak ada API AI pihak ketiga, label klinis, prediksi perkembangan, diagnosis, atau validasi klinis.
- `backend/app/repositories/observation_repository.py` dan launcher preview: sembilan catatan uji `DATA SINTETIS DEMO` hanya di-seed dengan flag preview eksplisit dan database terpisah. Catatan ini bukan training rows; bila mode demo aktif, hanya hitungan/aspek terstruktur yang menjadi masukan saat memilih ide umum. UI memberi label data sintetis dan batas klinis; keluarga tetap hanya melihat laporan/saran yang ditinjau dan dibagikan.
- Tes baru mencakup role escalation, seed/demo login, penerimaan bearer, startup fail-closed, seed sintetis opt-in/isolasi, evidence traceability, batas role, rate limiting, header, ukuran body, permission file, pencatatan konfirmasi parent offline, check-in/out, pencabutan izin penjemput, dan isolasi tenant.

## Verifikasi

- Backend: **64 tes lulus** pada putaran terbaru, termasuk isolasi tenant/admin, sensor per perangkat, insight berbasis bukti, pembaruan profil roster, relasi wali dua langkah, alur penjemput/check-in/out, pencabutan yang ditolak saat handover, migrasi additive status kehadiran lama, serta 96 skenario model aktivitas sintetis. Ada satu peringatan deprecation Starlette/httpx dari `TestClient`; bukan kegagalan tes.
- Frontend: TypeScript typecheck lulus; **5 tes client lulus**; build Next.js production lulus setelah perapian chat, relasi wali, edit profil roster, dan panel serah-terima penjemput yang responsif. Regresi CSP diuji: `'unsafe-eval'` ada hanya untuk Next development/preview dan tidak ada pada konfigurasi production.
- Dependency: `npm audit` = **0 advisori**; `pip-audit -r backend/requirements-dev.txt` = **No known vulnerabilities found** pada tanggal audit.
- Smoke test HTTP preview: halaman dashboard mengembalikan 200; admin/caregiver dapat membaca penjemput aktif sesuai role, audit kehadiran hanya admin, doctor tidak menerima nama penjemput, dan parent hanya membaca kehadiran anak tertaut. Endpoint profil/relasi wali dan status model sintetis juga merespons sesuai role. Browser visual/headless tidak dijalankan.
- Tes ini tidak membuktikan keamanan terhadap serangan nyata dan tidak menguji konfigurasi cloud/firewall/DNS/TLS produksi.

## Syarat minimum sebelum produksi

1. Tinjau/migrasikan semua aliran data dan endpoint terhadap fondasi `organization_id`/`child_id` yang sudah ditambahkan; lakukan onboarding tenant dan membership terkontrol, verifikasi relasi wali-anak dan identitas staf secara institusional, lalu lengkapi tes silang-tenant/IDOR untuk semua jalur/role. Sensor sejarah tanpa tenant dibiarkan tersembunyi karena kepemilikannya tak dapat dibuktikan.
2. Gunakan penyimpanan terkelola yang didukung, enkripsi transit dan at-rest, backup terenkripsi dan uji pemulihan, pengelolaan kunci/rotasi, serta kontrol akses host/database. Rancang penyimpanan foto privat, hapus metadata EXIF bila sesuai, dan sediakan penghapusan/pencabutan akses.
3. Tambahkan undangan staf, verifikasi email/identitas, MFA, pemulihan akun aman, penghentian akses staf, rotasi/revokasi sesi, rate limiting di gateway/WAF, dan perlindungan CSRF yang ditinjau untuk arsitektur produksi.
4. Rancang persetujuan yang dapat dibuktikan, pembatasan tujuan, retensi/penghapusan, audit append-only yang tidak memuat rahasia, minimisasi log, prosedur respons insiden, serta penilaian privasi/kewajiban hukum yang relevan.
5. Kode sensor kini memakai secret per perangkat/tenant. Sebelum produksi, tambahkan UI/API revokasi dan rotasi yang auditable, simpan secret di secret store perangkat, validasi TLS/perangkat, dan uji keamanan provisioning.
6. Jalankan threat modeling, uji penetrasi independen, pemindaian dependency/SBOM berkelanjutan, tinjau seluruh flow foto dan data kesehatan, dan uji restore serta respons kebocoran sebelum pilot.
7. Setelah semua blocker ditutup, tinjau ulang fail-closed production gate dan lakukan audit keamanan baru. Jangan menghapus gate hanya agar proses deploy berhasil.

## Pernyataan penggunaan

Untuk saat ini, gunakan hanya **profil/data/foto sintetis**. Jangan memasukkan nama, tanggal lahir, foto, catatan kesehatan, kredensial, atau informasi identitas anak nyata. Hasil KPSP tetap skrining dan memerlukan tinjauan dokter. Model demo ide aktivitas memang dilatih lokal pada skenario sintetis, tetapi belum divalidasi klinis dan bukan model perkembangan; insight bukan diagnosis.
